# ADR-002: Zepto MCP Authentication and Token Persistence

**Status:** Accepted

## Context

The Zepto MCP server requires OAuth authentication. The default FastMCP OAuth configuration successfully authenticates but does not persist credentials across process restarts by default.

The POC needs persistent authentication without requiring an OTP for every run. Stored credentials must also be encrypted at rest.

## Decision

Use FastMCP's OAuth implementation with persistent, encrypted token storage.

- **MCP server:** `https://mcp.zepto.co.in/mcp`
- **OAuth client:** FastMCP `OAuth`
- **Token storage:** `FileTreeStore`
- **Encryption:** `FernetEncryptionWrapper`
- **Encryption key:** Store separately at `~/.zepto-agent-key` with permissions `0600`.
- **Token storage directory:** `~/.zepto-agent-tokens`

Configure these three storage collections:

- `mcp-oauth-client-info`
- `mcp-oauth-token`
- `mcp-oauth-token-expiry`

Create the required directory hierarchy before initializing `FileTreeStore`.

Use FastMCP's dynamically registered OAuth client rather than hardcoding a client ID. Persist the client registration and tokens so subsequent runs can reuse them.

## Validation

- OAuth authentication succeeds.
- The MCP server's tools can be listed after authentication.
- Restarting the process reuses persisted credentials without requiring another OTP.

## Consequences

**Benefits**
- Avoids repeated interactive authentication.
- Keeps persisted OAuth data encrypted at rest.
- Separates the encryption key from the token data.

**Trade-offs**
- The encryption key must remain available and protected.
- Losing the key makes the encrypted token data unusable.
- OAuth storage depends on FastMCP's expected collection names and storage layout.

## Security Notes

- Do not commit the encryption key or token storage directory to source control.
- Restrict filesystem permissions on the key and token data.
- If credentials need to be reset, preserve or remove the token store deliberately and expect to authenticate again.
